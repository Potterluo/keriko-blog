手头有两篇讲 Agent 的文章，读完发现它们几乎不重叠。

一篇是从 Hucci 那期视频整理来的分层设计，讲「代码放在哪、边界怎么划、换模型换存储要动几个文件」。另一篇是 CookLLM 的《从聊天框到改代码》，讲一个 coding harness 要跑起来必须处理的六件事，每件事都对着真实代码。

前者给你可替换性，后者给你可用性。分开看各自都完整，合起来才能看清一个 Agent 系统真正的形状。

## 两篇各回答了什么

|            | 分层那篇                | harness 那篇                         |
| :--------- | :---------------------- | :----------------------------------- |
| 起点       | 一个 while 循环拆成三层 | 同一个模型为什么在聊天框里改不动仓库 |
| 回答的问题 | 东西放哪、怎么替换      | 一个循环里必须处理哪些事             |
| 产物       | 领域模型、接口、装配根  | 六个组件，每个几十行                 |
| 保证       | 换模型改一个文件        | 不会烧穿预算、不会跑出仓库、会话能续 |
| 缺的       | 权限、缓存、裁剪、委派  | 分层、审核、可替换性                 |

一句话概括：分层那篇画骨架，harness 那篇填血肉。

![图 1 两个视角的对位：左边是四件骨架，右边是六件血肉，箭头标出每个组件落在哪一层](/img/031-agent-skeleton-and-flesh/fig-01.svg)

## 骨架：四件事决定它能不能长大

这部分我上一篇拆得比较细，这里只留结论。

一是分层。领域层定义系统自己的语言（Session、Tool、Context），应用层编排流程，适配层把外部的东西翻译成自己的语言。

二是领域模型。对话是 `Session`，里面有 id 和消息列表；消息分 `UserMessage`、`AssistantMessage`、`ToolResult` 三种；工具调用单独定义成 `ToolCall`，带 id、名字、参数。

三是接口倒置。`SessionStore` 和 `ModelClient` 的接口写在应用层，实现在适配层。应用层只认接口，所以测试时能换内存实现，上线时能换 JSONL 或数据库。

四是装配根。整个系统里唯一知道所有具体类的地方，换模型、换存储、换前端入口都只改它。

这四件事的共同作用是把「变化」收敛到一个点上。代价是抽象层数变多，一个简单的循环被拆成五六个文件。

## 血肉：六件事决定它能不能跑

CookLLM 那篇的六个组件，正好补上分层没管的那些脏活。按它们落在骨架的哪一层，可以重新排一遍。

### 仓库现场：模型得知道自己站在哪

「把这个测试修好」不是一条完整指令。哪个仓库、哪个分支、有没有未提交的改动、项目文档怎么说构建和测试，这些不给模型，它只能猜。

`WorkspaceContext.build()` 在对话开始前一次性收集：`git rev-parse` 拿仓库根，`git status` 拿改动，最近五条 commit，然后按优先级找 `AGENTS.md`、`CLAUDE.md`、`README.md`、`pyproject.toml`、`package.json` 读进来。

两个细节值得学。`git()` 包了 try/except，不是 git 仓库就返回空字符串，harness 要面对各种真实项目，不能假设环境完美。主动捞项目文档这一步省掉一轮试错，因为文档里通常写着用什么命令跑测试。

按骨架的话，这是适配层的事：把文件系统和 git 的现状翻译成领域层认识的文本。

### 提示词形状：不变的在前，多变的在后

每一步推理发给模型的消息是「系统提示 + 压缩后的对话」。系统提示只放介绍、规则、仓库现场，一次会话里几乎不变。

这样做是为了配合前缀缓存。命中缓存的输入 token 和未命中的价格能差几十倍。如果把时间戳、随机排序的工具列表放在最前面，每步前缀都不同，缓存永远命中不了。反过来，只让对话尾部变化，缓存就能反复命中。

DeepSeek 的 `usage` 里有 `prompt_cache_hit_tokens`，多跑几步盯着这个数字就能看到缓存在工作。

这条在分层里没有位置，因为它是上下文组装顺序的约束，属于应用层里最容易被忽略的一段实现细节。

### 工具闸门：五道检查，一条路径规则

这是从聊天变成 agent 的地方。模型不能随手敲 shell，只能从固定工具里挑六个：`list_files`、`read_file`、`search`、`run_shell`、`write_file`、`patch_file`，后三个标了 risky。

每次调用都顺序过五关：是已知工具吗、参数合法吗、是危险操作吗、批准了吗、执行并裁剪输出。所有失败路径返回 `error:` 开头的字符串而不是抛异常，因为错误信息本身是喂给模型的反馈，模型看到 `old_text must occur exactly once, found 3`，下一步就会换更精确的匹配。

最能体现克制的是路径检查：模型给的路径一律不能逃出仓库根。`read_file ../../../etc/passwd` 在这里被直接拦掉。

### 上下文削减：近的保真，远的压缩

coding agent 会被自己的输出淹死。`clip()` 给单块文本封顶（4000 字），`compact()` 只裁剪老的工具结果，最近六条保持全保真，更早的压到 400 字。

这个判断很实用：十步前读过的文件模型大概率已经用完，留个摘要就够；最近一步的报错必须原样保留，因为那正是下一步要处理的东西。

### 转录与记忆：两层状态各管各的

第一层是完整转录，整段消息列表存盘，续跑时原样回放。第二层是工作记忆，一份模型自己维护的精简摘要：当前任务、正在动的文件、几条笔记。

记忆用一个小函数维护成「最近用过、不重复、有上限」的列表，读过的文件名上限 8 个。这样即便老的工具输出被裁掉了，「我们一直在围着 `tools.py` 转」这个事实仍然留着。

两层状态存进同一个 JSON，`--resume latest` 就能接着上次干。

### 有界委派：三个限制防住递归

主 agent 需要查支线时，派一个子 agent 去，只把结论带回来，别污染主上下文。

「有界」落在三处：子 agent 拿的是 `read_only=True` 的工具箱，只能看不能改；默认 `max_steps=3`；`depth < max_depth` 才注册 delegate 工具，于是主 agent 在 depth=0 有它，子 agent 在 depth=1 就没有，递归从结构上被掐断。

## 三个真正对不上的地方

对位表整理完，剩下三处是两篇之间需要拍板的地方，也是合起来看才有价值的部分。

### 一、Context 是两个东西

分层那篇里，`Context` 是领域对象：instruction、tools、history、output_type，是要发给模型的那一包东西。

harness 那篇里，`context.py` 是削减策略：clip 和 compact，是发给模型之前的加工过程。

同名不同义。这个重名恰好说明分层是必要的：概念在领域层，策略在应用层，两者用同一个词但活在两个位置。写代码时如果把它们塞进同一个类，测试会立刻变难，因为你要么为了测裁剪而构造一个完整上下文，要么为了测上下文而带上裁剪逻辑。

### 二、Tool 的定义少了风险字段

分层那篇的 `Tool` 只有四个成员：name、description、parameters、invoke。前三个给模型看，最后一个给人跑。

harness 那篇的工具有第五个属性：`risky`。没有它，`run()` 里的闸门就没法决定该不该停下来问人。

这类疏漏在领域建模时很常见：把面向模型的部分定义全了，忘了面向执行的部分还需要安全属性。按分层那篇的定义写完 Tool，等到接入真实执行环境时会发现字段不够，而加字段意味着改领域模型，改领域模型意味着全链路重编译。

提前想到的办法是把「谁能执行、要不要批准」也当成领域概念，哪怕具体策略由适配层决定。

### 三、审核有三个层次，不止一个

Hucci 的设计里，工具调用要再调一次模型审核：单独一个 `ToolCallReviewer` 角色，产出 `Decision`，包含能不能执行和拒绝原因。这是模型审。

CookLLM 的设计里，危险操作停下来问人（ask 模式）、信任时自动放行（auto）、彻底禁写（never）。这是人审。

两者不冲突，可以叠成三道闸：

| 顺序 | 闸门                   | 谁来做     | 拦住什么                                   |
| :--- | :--------------------- | :--------- | :----------------------------------------- |
| 1    | 参数 schema 与路径检查 | 代码       | 不认识的工具、非法参数、越界路径           |
| 2    | 权限批准               | 人         | 危险的写操作、跑命令                       |
| 3    | 模型审核               | 另一个模型 | 语义上不合理的调用，比如为了修测试去删测试 |

顺序不能反。schema 和路径检查最便宜，先跑；人审最慢，放在模型已经同意之后；模型审要花一次调用，放在中间。

![图 2 一次工具调用要过的三道闸：代码校验、人类批准、模型审核，顺序按成本从低到高](/img/031-agent-skeleton-and-flesh/fig-02.svg)

## 落地才会撞上的两件事

CookLLM 那篇记了两个只有真跑才会遇到的坑，值得单独抄下来。

第一，思考模式和工具调用可以同时开。老的 `deepseek-reasoner` 不支持 function calling，很多人因此默认「要工具就别开思考」。实测 V4 里两者可以并存，所以 client 无论开不开思考都把 tools 挂上。

第二，`reasoning_content` 喂回去会返回 400。思考模式下响应里 `content` 和 `reasoning_content` 是两个字段，直觉上你会把整个 assistant 消息原样追加进历史，下一轮就炸。必须在写进转录前把思维链剥掉，只保留 content 和 tool_calls。

连带的坑是 `max_tokens` 同时覆盖思维链和最终答案，预算给得抠，推理会先把额度吃光，`content` 为空、`finish_reason=length`。

按分层看，这两个坑都落在适配层：DeepSeek 的特殊字段和开关由适配层翻译，应用层不该知道 `reasoning_content` 这个词。如果你的实现让领域层或应用层出现了它，说明翻译动作做漏了。

## 收尾

两篇合起来，一个 Agent 系统的形状比较清楚了：

分层回答「变化来了改哪里」，六组件回答「一个循环里必须处理什么」，三道闸回答「危险动作在哪一层被拦住」。

判断一个实现是否成熟，可以看它有没有把这三件事分开。只做了循环的，能跑 demo；只做了分层的，能编译不好用；只做了六组件的，能改代码但换一次模型要动全身。

分开之后还有一处要留意：缓存、裁剪、记忆、委派这四件事都跟「上下文里有什么」有关，它们各自有效，叠加时会互相影响。压缩过的老消息什么时候被模型重新需要，现在没有好的答案，只能靠观察成本和效果。
