先看一段日志。这是我写完的 harness 在一个故意弄坏的仓库里跑出来的，任务只有一句「跑一下测试，把失败的修好」：

```text
[assistant] tools: run_shell
[tool] run_shell: FF                     # 两个用例失败
[assistant] tools: read_file, read_file
[tool] read_file: def add(a, b): ...
[assistant] 两个 bug 都清楚：add 用了减法，mean 多减了 1
[assistant] tools: patch_file
[review] patch_file -> approved
[tool] patch_file: patched calc.py (1 replacement)
[assistant] tools: run_shell
[tool] run_shell: ..                     # 通过
[assistant] 测试全部通过。
```

看起来平平无奇。但这段日志能成立，背后压着七层东西；任何一层抽掉，它就跑不出来。这篇文章从日志往回拆。

代码在 [Potterluo/mini-agent-harness](https://github.com/Potterluo/mini-agent-harness)，11 个文件约 1700 行，16 个提交，101 个测试，模型是 `deepseek-v4.1-flash`。

![图 1 日志的每一行背后都压着一层：现场、工具、闸门、裁剪、记忆、委派、可替换](/img/032-building-a-harness/fig-01.svg)

## 第一层：它凭什么知道自己在哪个仓库

日志第一行是 `run_shell: FF`，两个 F 代表两个失败的用例。这两个 F 有意义的前提，是那条命令跑在了正确的目录里。

「把测试修好」不是一条完整指令。模型得先知道：这是哪个仓库、当前什么分支、有没有未提交的改动、项目自己写的文档怎么说构建和测试。这些不给它，它只能猜，而猜错的代价是改错文件。

所以会话开始前先收一次现场：仓库根、分支、`git status`、最近五条提交，再按优先级读 `AGENTS.md`、`CLAUDE.md`、`README.md`、`pyproject.toml`、`package.json`。收完折进系统提示，整个会话只构造一次。

这里有个小设计：所有 git 命令都包了一层降级。

```python
def git(*args, fallback=""):
    try:
        ...
        return done.stdout.strip() or fallback
    except Exception:
        return fallback
```

harness 要面对各种真实项目，不是每个目录都是 git 仓库。崩掉和降级之间，差的是「能不能用」。

拆掉这一层：模型凭文件名猜结构，第一行命令就跑到别的目录去了。

## 第二层：它凭什么能动手

日志里的 `read_file`、`patch_file`、`run_shell`，都是模型自己做不到的动作。它只会输出文本。

能动手的前提是把动作收窄成固定的一组工具：列目录、读文件、搜索、跑命令、写文件、改一处文本。模型只能从这六个里挑，不能凭空敲命令。

工具的领域定义是五个成员，前四个给模型看，最后一个给执行层看：

```python
class Tool(Protocol):
    name: str            # 模型靠它点名
    description: str     # 模型靠它判断用途
    parameters: dict     # 模型靠它知道传什么
    risky: bool          # 执行层靠它决定要不要过人工闸
    def invoke(self, arguments: dict) -> str: ...
```

`risky` 是我在设计阶段特意加的。当时犹豫过：它跟模型无关，是不是该放到执行层去？后来想明白，判断一个工具危不危险，是工具本身的属性，不是某次调用的属性。漏了它，等接真实闸门时会发现字段不够，而改领域模型意味着全链路重编译。

拆掉这一层：给模型一个裸 shell，日志第一行可能就是 `rm -rf`。

## 第三层：谁敢批准它动手

这是整段日志里最容易被忽略的一行：

```text
[review] patch_file -> approved
```

`patch_file` 是危险操作，改了 `calc.py`。谁同意的？三个角色，按成本从低到高排队：

| 顺序 | 闸门               | 谁来做     | 拦住什么                         |
| :--- | :----------------- | :--------- | :------------------------------- |
| 1    | 参数校验与路径检查 | 代码       | 不认识的工具、非法参数、越界路径 |
| 2    | 人工批准           | 人         | 危险的写操作                     |
| 3    | 模型审核           | 另一个模型 | 为了修测试去删测试               |

顺序不能反。代码检查最便宜，先跑；人最慢，放在模型已经同意之后；模型审核要花一次推理，放中间。

![图 2 模型想动手，先过三道闸：代码校验、人工批准、模型审核，成本从低到高](/img/032-building-a-harness/fig-02.svg)

第三道闸是我踩坑最多的地方，值得单独说。

第一版我把整段对话历史丢给审核模型，让它判断这次调用该不该执行。结果它不回判断，继续调工具：

```text
[review] run_shell -> rejected reviewer returned unparsable output:
finish_reason=tool_calls, usage={'prompt': 594, 'completion': 44}
```

`finish_reason` 是 `tool_calls`。它顺着历史里助手的说话方式，接着往下干活了。历史里全是我调工具的记录，它自然认为自己也该调。

改成只给三样：当前任务、最近几条工具结果、待审的那次调用，历史清空。

改完仍有大量空回复。根因更隐蔽：审核发生在工具执行之前，此时 session 末尾是一条带 `tool_calls`、却还没有对应 `tool` 结果的助手消息。这种序列发给模型不合法，网关直接返回空内容。

```python
history = list(session.messages)
if history and isinstance(history[-1], AssistantMessage) and history[-1].tool_calls:
    history.pop()
```

剥掉这条悬空消息，审核才稳定下来。

拆掉这一层：模型可以为了「让测试通过」把测试删掉，而且日志里看不出异常。

## 第四层：它怎么不把自己撑死

日志里第二次 `read_file` 之后其实还有若干次读取和命令输出。每次工具返回的内容都会塞回上下文，塞得越多，下一步越慢、越贵、越容易犯糊涂。

两条便宜的策略。第一条给单块输出封顶，4000 字，超出截断并注明切掉了多少。

第二条只压老的工具结果：

```python
def compact(messages, keep_recent=6, old_limit=400):
    # 最近六条工具结果保持全保真，更早的压到 400 字
```

这个取舍值得记：十步前读过的文件，模型大概率已经用完，留个摘要就够；最近一步的报错必须原样保留，因为那正是下一步要处理的东西。

拆掉这一层：跑到第十步上下文就满了，表现为「模型变笨」，其实是上下文质量下降。

## 第五层：它怎么记得住

日志跑完，进程退出，任务结束。真实场景里任务会被打断，晚上关掉，第二天接着干。

所以每步都落盘：完整转录存一份，工作记忆存一份。工作记忆记三样东西：当前任务、正在动的文件、几条笔记，列表有上限且去重。

这一层我做得不完整，得说实话。结构定义好了，转录也确实每步在存，但「把用过的文件记进 files」这个动作没有接进主循环。对比过另一个实现之后才发现：记忆的难点在每一轮都要真的记账，光把结构定义出来不算。

拆掉这一层：断一次全部白干。

## 第六层：它怎么不越帮越忙

日志里没有出现委派，因为任务是小事。但复杂任务里，主 agent 常常需要先查一个支线问题，比如「`context.py` 到底怎么裁剪的」。把这种调查塞进主对话，会把上下文搅浑。

做法是派一个子 agent 出去，只把结论带回来。绳子要拴紧，落在三处：子 agent 拿只读工具箱、步数默认 3、深度到了上限就不再注册 delegate。最后这条从结构上掐断递归，不靠提示词自律。

拆掉这一层：支线调查污染主线，或者更糟，子 agent 再派子 agent，一层层烧钱。

## 第七层：换一个模型要改几行

日志里看不出这一层，因为它不出现在运行轨迹里，只出现在你改需求的那天。

`SessionStore`、`ModelClient`、`Approver` 三个接口定义在应用层，实现放在适配层。换模型、换存储、换前端入口，只改装配根一个文件。

```python
class ModelClient(Protocol):
    def generate(self, context: Context, setting: ModelSetting) -> Any: ...
```

这条的好处不在生产环境，在测试里立刻兑现：把 `ModelClient` 换成按脚本回放的假客户端，循环的四种分支（正常、审核拒绝、批准拒绝、步数上限）全都能覆盖，一次 0.4 秒，不花钱。

拆掉这一层：每加一家模型，就要在循环里加一层 if；测试永远得真调接口。

## 拆完之后，剩下三处裂缝

七层都补上，日志能跑了。但真跑过程中还有三处裂缝，它们不在设计图里，只在运行时出现。

第一处是平台的。这台机器默认 GBK，撞了三次：命令行打印中文、子进程抓输出、`git status` 遇到中文文件名。三处都得显式指定 UTF-8。不影响架构，但会让「明明代码没错」的排查耗掉一晚上。

第二处是协作的。写的时候开了两个子 agent 并行，一个写工具闸门，一个写上下文和存储。提示里写了「只碰这两个文件」，但漏了 `roles.py` 的归属，两边都以为自己可以动它，短暂出现 `NameError: ToolResult 未定义`。文件归属比接口归属更容易被忽略：接口是显式的，编译期会报；文件是隐式的，跑到一半才炸。

第三处是语义的，也是最有价值的那个：审核模型的判断质量，取决于你给它的上下文有多干净。给它整段历史，它就变成另一个助手；只给它三样，它才是个审核员。这条经验没法从接口设计里推出来，只能靠跑。

## 回到那八行

现在再看开头那段日志：

`run_shell: FF` 背后是现场收集与路径闸；`read_file` 背后是工具集与输出裁剪；`review → approved` 背后是三道闸与消息序列的合法性；`patched calc.py` 背后是人工批准；`..` 背后是上下文没被撑爆；`测试全部通过。` 背后是主循环在正确的时候停下来。

七层里最容易搞错的是它们的顺序：先定概念、再定接口、最后填实现。概念定错，后面全要返工；接口定错，测试写不出来；顺序反了，就会在写第三层时发现第一层缺字段。

代码和同样的脉络在 [GitHub](https://github.com/Potterluo/mini-agent-harness)。
