## 一、Agent 是怎么跑起来的

一个大模型能做的只有一件事：给一段文本，返回一段文本。它能写代码、能讲原理，但它看不到你的仓库，改不了文件，也跑不了测试。

所谓 Agent，是把这次「文本进、文本出」包装成一个循环：

```
读现场 → 让模型决策 → 执行它要的动作 → 把结果反馈回去 → 再决策
```

循环通常在两种情况下停：模型不再要求动作、只回一段文本；或者达到步数上限。

这个循环本身很小，几十行就能写完。真正让它变成可用系统的东西在循环外面，业内一般叫 harness：

- 它决定模型每次开口前看到什么（现场、历史、工具说明）
- 它决定模型能做什么动作（工具集、参数、权限）
- 它决定动作的后果怎么处理（执行、裁剪、回填、审核）
- 它决定状态存在哪、断了怎么续

同一段循环，配一个简陋的壳，就是「会读文件的聊天机器人」；配一个完整的 harness，就是 Claude Code、Cursor 这类工具。差别不在模型，在这层壳。

![图 1 Agent 的最小循环：每次迭代都是「模型决策 → 执行动作 → 反馈结果」，harness 负责这四步之外的所有事](/img/032-building-a-harness/fig-01.svg)

## 二、一个具体的场景

光说概念没用，给一个具体任务。

我在本地造了个小仓库 `demo-repo`，只有两个文件：`calc.py` 和 `test_calc.py`。`calc.py` 里两个函数都被改坏了：

```python
def add(a, b):
    return a - b          # 应该是加


def mean(values):
    return sum(values) / len(values) - 1   # 多了个 -1
```

`python -m unittest` 跑出来两个用例全红。任务只有一句：

> 跑一下测试，把失败的修好。只改 calc.py。

如果只用一个裸循环，也就是「把用户消息发给模型，模型回什么就打印什么」，会依次撞上六堵墙：

| 撞上的墙       | 具体表现                                                       |
| :------------- | :------------------------------------------------------------- |
| 不知道自己在哪 | 模型只能凭文件名猜结构，第一条命令可能跑在错误的目录           |
| 动不了手       | 它只能说「把 a - b 改成 a + b」，改文件要人来复制粘贴          |
| 拦不住         | 就算接上了 shell，模型也可能为了「让测试通过」把测试删掉       |
| 看不全         | 每次读文件、跑命令的输出都塞回上下文，十几步就撑满             |
| 记不住         | 进程一断，前面几十步全白干                                     |
| 会跑偏         | 想查个支线问题，把主上下文搅浑；或者子任务再派子任务，层层烧钱 |

这六堵墙构成了需求清单。

## 三、产品设计：harness 该提供什么

从六堵墙反推，需要的是一组能力，而不是一堆功能：

| 能力       | 对应需求                                   | 不做会怎样                   |
| :--------- | :----------------------------------------- | :--------------------------- |
| 现场注入   | 会话开始前收集仓库根、分支、改动、项目文档 | 模型靠猜，改错文件           |
| 固定工具集 | 六个受限动作，参数有 schema                | 模型乱敲命令                 |
| 分级授权   | 危险操作需要批准，越界路径直接拒           | 跑出仓库、误删文件           |
| 上下文管理 | 单块封顶、老结果压缩、近期保真             | 窗口撑满，表现为「模型变笨」 |
| 状态持久化 | 每步落盘，可按会话续跑                     | 中断即丢失                   |
| 委派隔离   | 子 agent 只读、步数更少、不能再派          | 支线污染主线，递归烧钱       |

再补三条工程约束，决定这套东西能不能被长期维护：

1. 换模型、换存储、换前端入口，不改核心逻辑。
2. 测试不依赖真实模型调用。
3. 在 Windows 上能跑。

明确不做的部分同样重要：不做并行工具调用、不做摘要式压缩、不做多模态、委派只允许一层。这些是范围，不是缺陷。

验收标准也跟着定下来了，每条都要能被测试断言：

| 能力       | 验收方式                                                  |
| :--------- | :-------------------------------------------------------- |
| 现场注入   | 非 git 目录下不报错，返回降级结果                         |
| 固定工具集 | 未知工具、缺参数、错类型都返回可读错误                    |
| 分级授权   | `../../etc/passwd` 被拒且不落盘；只读模式下三个写工具全拒 |
| 上下文管理 | 单块输出不超 4000 字；最近六条工具结果原样保留            |
| 状态持久化 | 存盘后读回，三种消息与记忆都能还原                        |
| 委派隔离   | 子 agent 的工具箱里没有 delegate                          |

## 四、架构设计：三层与四个抽象

有了需求和验收，才轮到分层。分层的目的写在需求里：换模型不改核心、测试不花真钱。这两条直接决定了依赖方向。

### 4.1 三个抽象层

领域层定义系统自己的语言，不认识任何外部协议。应用层编排流程，只依赖接口。适配层把仓库、文件、模型翻译成领域对象。最上面是装配根，唯一知道所有具体类的地方。

| 层     | 放什么                                 | 判断标准                       |
| :----- | :------------------------------------- | :----------------------------- |
| 领域层 | Session、消息、Tool、Context、Decision | 换任何外部服务，这一层都不用改 |
| 应用层 | 循环、角色、上下文组装、接口定义       | 只 import 领域层               |
| 适配层 | 文件系统、git、模型 API、JSON 存储     | 实现应用层的接口               |
| 装配根 | 创建具体类、接线                       | 唯一 import 适配层的地方       |

![图 2 分层与依赖方向：应用层只认接口，适配层负责兑现，装配根负责接线](/img/032-building-a-harness/fig-02.svg)

### 4.2 四个抽象

抽象不是越多越好，这四个刚好够用。

Session 与消息。 对话是系统最外层的表现形态，用 `Session` 表达：一个 id，一个消息列表，一份工作记忆。消息分三种。

```python
UserMessage(text)
AssistantMessage(text, tool_calls)
ToolResult(tool_call_id, content)
```

工具调用单独定义成 `ToolCall(id, name, arguments)`。`id` 不是装饰，它是把「模型要的动作」和「动作的结果」对上的唯一凭据。

Tool。 五个成员，前四个给模型看，最后一个给执行层看。

```python
class Tool(Protocol):
    name: str
    description: str
    parameters: dict
    risky: bool
    def invoke(self, arguments: dict) -> str: ...
```

`risky` 值得单独说明。它跟模型无关，看起来该放到执行层，但「这个工具危不危险」是工具本身的属性，不是某次调用的属性。放在这里，执行层才知道该不该停下来问人。

Context。 发给模型的那一包东西，带一个泛型的输出类型。

```python
@dataclass
class Context(Generic[OpType]):
    instruction: str
    tools: list[Tool]
    history: list[Message]
    output_type: type[OpType]
```

这个泛型让同一套组装逻辑服务两个角色：回复用户时输出 `AssistantMessage`，审核工具调用时输出 `Decision`。少写一份组装代码，也少一次不一致的机会。

三个接口。 `SessionStore`、`ModelClient`、`Approver`，全部是 Protocol。

```python
class ModelClient(Protocol):
    def generate(self, context: Context, setting: ModelSetting) -> Any: ...
```

### 4.3 怎么往上加瓦

这套结构的价值不在第一次写完，在后续每一次加能力。加瓦的路线是固定的四步：先在领域层问这件事需不需要新概念，再看应用层谁来编排，然后适配层怎么做翻译，最后装配根接线一行。

用这次实际加的三块做例子：

| 新增能力 | 领域层改动            | 应用层改动                        | 适配层改动          | 装配根改动   |
| :------- | :-------------------- | :-------------------------------- | :------------------ | :----------- |
| 模型审核 | 新增 `Decision`       | 新增 `ReviewerRole`，循环里插一道 | 无                  | 多传一个角色 |
| 工作记忆 | 复用 `Session.memory` | 循环里加记账                      | 存储已支持          | 无           |
| 有界委派 | 复用 `Tool`           | 无                                | 新增 `DelegateTool` | 按深度注册   |

三块里有两块没动领域层，这是分层真正省事的地方：概念够用的时候，新增能力只碰一处。

## 五、实现：从循环到系统

提交顺序就是依赖顺序，每个提交都能独立通过全部测试。

| 提交                    | 内容                                       | 层       |
| :---------------------- | :----------------------------------------- | :------- |
| `chore: 初始化项目骨架` | pyproject、目录                            | 无       |
| `feat(domain)`          | Session、三类消息、Tool、Context、Decision | 领域     |
| `feat(ports)`           | 三个协议                                   | 应用     |
| `feat(context)`         | clip 与 compact                            | 应用     |
| `feat(session)`         | JSON 持久化、工作记忆                      | 适配     |
| `feat(tools)`           | 六个工具与五道闸                           | 适配     |
| `feat(workspace)`       | 仓库现场与项目文档                         | 适配     |
| `feat(client)`          | OpenAI 兼容客户端                          | 适配     |
| `feat(service)`         | 两个角色与主循环                           | 应用     |
| `feat(runtime)`         | 装配根与命令行                             | 装配根   |
| `test: 主循环集成测试`  | 假客户端回放                               | 测试     |
| `feat(delegate)`        | 有界委派                                   | 适配     |
| `fix(service)`          | 工具执行后写工作记忆                       | 应用     |
| 三个 `fix`              | 实跑暴露的问题                             | 见第七节 |

几个关键实现。

### 5.1 现场注入

会话开始前收一次：仓库根、分支、`git status`、最近五条提交，再按优先级读 `AGENTS.md`、`CLAUDE.md`、`README.md`、`pyproject.toml`、`package.json`，折进系统提示，整个会话只构造一次。

所有 git 命令都包一层降级，不是 git 仓库就返回空字符串，而不是崩掉。harness 要面对各种真实项目，不能假设环境完美。

### 5.2 工具与五道闸

每次调用顺序过五关，失败一律返回 `error:` 开头的字符串。

```python
def run(self, name, arguments):
    tool = self._by_name.get(name)
    if tool is None:
        return f"error: unknown tool '{name}'"
    try:
        self._validate(tool, arguments)
    except ValueError as exc:
        return f"error: invalid arguments for {name}: {exc}"
    ...
```

不抛异常，是因为错误信息本身是反馈。模型看到 `old_text must occur exactly once, found 3`，下一步就会换一个更精确的匹配；抛异常只会让整个循环崩掉。

### 5.3 三道闸

危险动作的批准分三层，按成本从低到高排队。

![图 3 一次工具调用要过的三道闸：代码校验、人工批准、模型审核](/img/032-building-a-harness/fig-03.svg)

第三道闸是可选件，因为它要花一次模型调用。它的价值在后面会看到：判断「这个动作服务于任务吗」需要语义能力，光靠 schema 做不到。

### 5.4 上下文削减

两条便宜的策略。单块输出封顶 4000 字。

```python
def compact(messages, keep_recent=6, old_limit=400):
    """最近六条工具结果原样保留，更早的压到 400 字。"""
```

取舍的依据是时间相关性：十步前读过的文件，模型大概率已经用完；最近一步的报错，正是下一步要处理的东西。

### 5.5 记忆与续跑

每步落盘，完整转录一份，工作记忆一份。工作记忆记三样：当前任务、动过的文件、工具笔记，列表有上限且去重。

这里我一开始只做了结构，没做记账，第一次跑完才发现记忆是空的。补上之后，才算真的能在压缩上下文之后仍记得「我们一直在围着 `calc.py` 转」。

### 5.6 有界委派

子 agent 拿只读工具箱、步数默认 3、深度到顶就不再注册 `delegate`。最后一条从结构上掐断递归，不靠提示词自律。

## 六、验证：测试与真实运行

### 6.1 测试策略

103 个用例，全部用临时目录和假模型客户端，不联网，跑完不到一秒。

关键在于 `ModelClient` 是协议：假客户端按脚本回放，就能覆盖循环的四种分支（正常结束、审核拒绝、批准拒绝、步数上限），不需要真调接口。这是第三节里「测试不依赖真实模型」那条约束的直接兑现。

### 6.2 真实运行

用 `deepseek-v4.1-flash` 在 `demo-repo` 上跑了一次，任务照旧：

```text
[assistant] tools: run_shell
[tool] run_shell: FF                     # 两个用例失败
[assistant] tools: read_file, read_file
[tool] read_file: def add(a, b): ...
[assistant] 两个 bug 都清楚：add 用了减法，mean 多减了 1
[assistant] tools: patch_file
[review] patch_file -> approved
[tool] patch_file: patched calc.py (1 replacement)
[assistant] tools: run_shell
[tool] run_shell: ..                     # 通过
[assistant] 测试全部通过。
```

代价是 8 次模型调用和几百毫秒的工具耗时，每一步都留在会话文件里可回溯。改动落在一个文件的两处函数，符合「只改 calc.py」的约束。

## 七、复盘：四处裂缝与后续

设计和实现都能讲清楚，但真跑起来的坑不在设计图里。四个都是实测才暴露的。

审核角色会扮演助手。 最初把整段对话历史丢给审核模型，它不回判断，而是顺着历史继续调工具，`finish_reason=tool_calls`，一个字都不回。改成只给三样：当前任务、最近几条工具结果、待审的那次调用。这条经验没法从接口设计里推出来。

悬空的 tool_call。 审核发生在工具执行之前，此时 session 末尾是一条带 `tool_calls`、却还没有对应 `tool` 结果的助手消息。这种序列不合法，网关直接返回空内容。审核前先摘掉它。

Windows 三处编码。 控制台、子进程输出、`git status`，默认 GBK，遇到中文就抛异常，都要显式指定 UTF-8。

并行改同一个文件。 两个子 agent 并行时漏了 `roles.py` 的归属，一个在重写、另一个在跑测试，短暂出现 `NameError`。文件归属比接口归属更容易被忽略：接口是显式的，编译期会报；文件是隐式的，跑到一半才炸。

已知不足也列在这：不做并行工具调用、不做摘要式压缩、委派只有一层、没有多模态输入。下一步最想补的是摘要式压缩，因为现在裁剪老结果时，被压掉的细节再也回不来了。

代码在 [Potterluo/mini-agent-harness](https://github.com/Potterluo/mini-agent-harness)，README 按同样的顺序组织，clone 下来配上自己的 key 就能跑。
