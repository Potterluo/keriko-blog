## 一、Agent 是怎么跑起来的

一个大模型能做的只有一件事：给一段文本，返回一段文本。它能写代码、能讲原理，但它看不到你的仓库，改不了文件，也跑不了测试。

所谓 Agent，是把这次「文本进、文本出」包装成一个循环：

```
读现场 → 让模型决策 → 执行它要的动作 → 把结果反馈回去 → 再决策
```

循环在两种情况下停：模型不再要求动作、只回一段文本；或者达到步数上限。前者是正常结束，后者是安全阀，因为模型完全可能陷进「反复读同一个文件」这样的死循环，没有上限，一次失误就能烧光预算。

这个循环本身很小，几十行就能写完。真正让它变成可用系统的是循环外面那层东西，业内一般叫 harness。它管四件事：模型每次开口前看到什么（现场、历史、工具说明）；它能做什么动作（工具集、参数、权限）；动作的后果怎么处理（执行、裁剪、回填、审核）；状态存在哪、断了怎么续。

同一段循环，配一个简陋的壳，就是「会读文件的聊天机器人」；配一个完整的 harness，就是 Claude Code、Cursor 这类工具。差别不在模型，在这层壳。这篇文章要做的事，就是把这层壳从零写一遍，并且把每个设计决定的理由讲清楚。

![图 1 Agent 的最小循环：每次迭代都是「模型决策 → 执行动作 → 反馈结果」，harness 负责这四步之外的所有事](/img/032-building-a-harness/fig-01.svg)

## 二、一个具体的场景

概念讲完了，给一个具体任务，否则后面的设计没有落点。

我在本地造了个小仓库 `demo-repo`，只有两个文件：`calc.py` 和 `test_calc.py`。`calc.py` 里两个函数都被改坏了：

```python
def add(a, b):
    return a - b          # 应该是加


def mean(values):
    return sum(values) / len(values) - 1   # 多了个 -1
```

`python -m unittest` 跑出来两个用例全红。任务只有一句：「跑一下测试，把失败的修好。只改 calc.py。」

现在想象用一个裸循环来应对：把用户消息发给模型，模型回什么就打印什么。第一步就会卡住，因为模型只能说「把 a - b 改成 a + b」，改文件要人来复制粘贴。好，那就给它接一个 shell。第二步卡住：它不知道自己在哪个目录，第一条命令可能就跑错地方，于是再喂仓库结构。第三步还是卡：跑测试的输出、读文件的内容都塞回上下文，十几步之后窗口满了，模型开始「变笨」，其实只是它看到的东西质量在下降。第四步，进程一断，前面几十步全白干。第五步，任务稍微复杂点，它想先查个支线问题，查完的过程和结论一起挤进主对话，主线被搅浑。

把这五步串起来，就是裸循环的六堵墙：不知道自己在哪、动不了手、拦不住（比如为了「让测试通过」直接删测试）、看不全、记不住、会跑偏。这六堵墙全部来自这个具体场景，一步一步撞出来的，没有一条是从别处抄来的。它们构成了 harness 的全部需求。

## 三、产品设计：harness 该提供什么

六堵墙每堵都对应一种能力：不知道在哪 → 会话开始前注入现场；动不了手 → 固定的受限工具集；拦不住 → 分级授权；看不全 → 上下文管理；记不住 → 状态持久化；会跑偏 → 委派隔离。

![图 2 六堵墙与六种能力的对应：左边一步一步撞出来，右边各有一个解法和落点](/img/032-building-a-harness/fig-02.svg)

能力之间不重叠，也不互相依赖，每一堵墙一个解法，这是第一层设计。

比功能更重要的是三条工程约束，它们决定这套东西能不能被长期维护。第一，换模型、换存储、换前端入口，不改核心逻辑。模型协议半年一变，如果每变一次都要动主循环，这个系统的寿命就跟某一家厂商绑定死了。第二，测试不依赖真实模型调用。测试要跑得频繁才有用，一次几毛钱的测试不会有人频繁跑。第三，在 Windows 上能跑，这只是作者的现实约束，但它逼出了一个更一般的要求：不要假设环境完美。

也要明确不做什么：不做并行工具调用、不做摘要式压缩、不做多模态、委派只允许一层。范围和功能一样是设计的一部分，这些不做的理由会在复盘里看到。

验收标准跟着需求走，每条都能被测试断言：非 git 目录下不报错而是降级；未知工具和错误参数返回可读的错误字符串；`../../etc/passwd` 被拒且不落盘；单块输出不超过 4000 字且最近六条工具结果原样保留；会话存盘再读回，消息和记忆都不丢；子 agent 的工具箱里没有 delegate。到这一步，需求、约束、范围、验收都齐了，才轮到架构。

## 四、架构设计：三层是怎么被逼出来的

先说清楚一件事：三层的数量由第三节的约束推出来，让我凭感觉选，未必会停在三层。下面把推导过程走一遍，比结论本身重要。

### 4.1 第一刀：概念与协议分开

假设不分层，把循环、消息、工具执行、模型调用、存储全部写进一个文件。第一次跑通没问题，问题出在第一次改动。想换一家模型，请求格式、参数名、思维链字段全埋在循环中间，你得在循环里到处找地方打补丁；想测试循环，`generate` 直接打真接口，几十个用例跑一次几十块钱。

问题的根源是两种代码被搅在一起了。一种描述「系统是什么」：对话、消息、工具、上下文，这套词跟任何厂商无关。另一种描述「怎么跟外部说话」：模型 API 的字段名、文件系统的路径规则、git 的输出格式。前一种变化慢，后一种变化快。

所以第一刀切在这两者之间：描述系统自己的语言归领域层，跟外部协议打交道的归适配层。判断标准只有一句话：换任何一家外部服务，领域层一行都不用改。这句话同时也是测试，写完领域层之后问自己，把模型从 DeepSeek 换成别的，`Session` 要改吗？`ToolCall` 要改吗？不要，就对了。

### 4.2 第二刀：编排与实现分开

有了两刀之后的新问题是：应用层的循环要调模型、要存会话，它 import 谁？如果 import 适配层里具体的 `OpenAIChatClient`，换模型还是要改循环，第一刀白切了。

解法是把「需要什么」和「怎么做到」拆开：接口定义在应用层，实现在适配层。`ModelClient` 说清楚循环需要 `generate(context, setting)` 这个动作，至于是谁实现的，循环不知道也不关心。依赖方向从「应用层依赖适配层」翻转成「适配层依赖应用层的接口」，它在教科书里叫依赖倒置，但把它请进这个项目的理由很具体：换模型不能改循环。

第二条约束「测试不花钱」也在这里兑现：`ModelClient` 是个协议，测试里塞一个按脚本回放的假客户端，循环的四种分支（正常结束、审核拒绝、批准拒绝、步数上限）全部离线覆盖。没有这一刀，这些分支只能打真接口验证。

### 4.3 第三刀：留一个接线的洞

接口和实现都齐了，还剩一个最容易被忽略的问题：谁把具体类创建出来、接到一起？如果任何地方都能 `OpenAIChatClient(...)`，具体类的引用就散回各处，前面两刀又白切了。

所以留一个装配根，全系统唯一 import 适配层的地方。它做一件事：创建具体类，接上接口。换模型改这里一行，换存储改这里一行，换前端入口还是改这里。判断标准也很直白：全仓库 grep 适配层的类名，应该只命中装配根一个文件。

### 4.4 三层的由来

现在数一下：第一条约束（换模型不改核心）逼出第一刀和第三刀，第二条约束（测试不花钱）逼出第二刀，接线问题天然需要一个收口。三层的数量等于约束的数量，跟审美无关。如果还有第三条硬约束，比如「同一份代码要跑在沙箱里」，那才会有第四层；没有那条约束，多出来的层就是纯开销。

![图 3 三层与四个抽象：层由约束切出来，领域层里的四个抽象各回答循环里的一个问题](/img/032-building-a-harness/fig-03.svg)

### 4.5 层里放什么：四个抽象

层定好了，里面放什么。四个抽象也是被问题逼出来的，每个回答循环里的一个问题，检验方式都一样：删掉它，哪段代码会变形。

对话是什么，`Session` 回答。它是一个 id、一个消息列表、一份工作记忆。消息分三种：用户说的、模型说的、工具干的。模型说的那种可以带 `tool_calls`，每个 `ToolCall` 有自己的 id，这个 id 不是装饰，它是把「模型要的动作」和「动作的结果」对上的唯一凭据，没有它，多工具调用的回填就对不上号。

动作是什么，`Tool` 回答。五个成员：name、description、parameters 给模型看，invoke 给执行层看。`risky` 值得单独讲。它跟模型无关，看起来该放执行层，但「这个工具危不危险」是工具本身的属性，不是某次调用的属性，run_shell 无论被谁、为什么调用都是危险动作。放在领域层，执行层的闸门才有依据。这个字段是我设计时犹豫最久的一个，也是后来最庆幸加了的一个：漏了它，接闸门时就要改领域模型，而改领域模型意味着全链路重编译。

模型每次看到什么，`Context` 回答。它带一个泛型的输出类型，动机很具体：回复用户和审核工具调用是两种任务，输出类型不同（前者 `AssistantMessage`，后者 `Decision`），但组装上下文的逻辑完全一样。泛型让同一套机制服务两个角色，少写一份代码，也少一次不一致的机会。

一次动作由谁说了算，`Decision` 和三个接口回答。`Decision(approved, reason)` 是审核的结论，拒绝时必须带原因，因为原因会作为工具结果交还给模型，它需要知道为什么被拦才能换策略。`SessionStore`、`ModelClient`、`Approver` 三个协议就是 4.2 里说的接口，不再展开。

### 4.6 怎么往上加瓦

这套结构的价值不在第一次写完，在后续每一次加能力。加瓦的路线是固定的四步：先在领域层问这件事需不需要新概念，再看应用层谁来编排它，然后适配层做翻译，最后装配根接线一行。

用这次实际加的三块验证。加模型审核：领域层加一个 `Decision` 类型（新概念，审核结论以前不存在），应用层加一个 `ReviewerRole` 并在循环里插一道，适配层无改动，装配根多传一个角色。加工序记忆：领域层零改动（复用 `Session.memory`），应用层在循环里加记账，适配层的存储早就支持 dict。加有界委派：领域层零改动（delegate 就是一个 Tool），应用层零改动，适配层加一个 `DelegateTool`，装配根按深度注册。

三块里两块没动领域层。这是分层真正的收益所在：概念层稳定之后，新能力大多只碰一个文件。反过来，如果每次加功能都要动 `Session` 或 `Tool`，说明领域建模漏了东西，那是比写新代码更贵的信号。

## 五、实现：从循环到系统

设计讲完，实现反而是最顺的部分。提交顺序就是依赖顺序：骨架、领域、接口先落地，然后每个提交填一块能力，每个提交单独可测。16 个提交里没有一个是「大爆炸」，最长的 diff 也不超过三百行。

具体顺序：`domain`（Session、消息、Tool、Context、Decision）→ `ports`（三个协议）→ `context`（裁剪）→ `session`（存储）→ `tools`（工具与闸门）→ `workspace`（现场）→ `client`（模型协议）→ `service`（循环与角色）→ `runtime`（装配根与命令行）→ 集成测试 → `delegate` → 一个补记忆记账的 fix → 三个实跑暴露的 fix。这个顺序的好处是每一步的验证都只依赖前面已提交的东西，不用「等全部写完才能跑」。

几个值得讲理由的实现选择。

现场注入放在会话开始，只做一次。仓库根、分支、status、最近五条提交，加上按优先级读的 `AGENTS.md`、`README.md`、`pyproject.toml`。所有 git 命令都包一层降级，不是 git 仓库就返回空字符串。理由是第三节的验收第一条：harness 要面对各种真实项目，崩掉和降级之间差的是「能不能用」。

工具闸门五道检查，失败一律返回 `error:` 开头的字符串而不是抛异常。理由：错误信息是给模型的反馈，不是日志。模型看到 `old_text must occur exactly once, found 3`，下一步就会换一个更精确的匹配；抛异常只会让整个循环崩掉，模型失去纠偏的机会。

危险动作的批准分三层，按成本从低到高：代码校验几乎免费先跑；人最慢，放在模型已经同意之后；模型审核要花一次推理，放最后。顺序反了会怎样？人审放第一位，每条无害的 `read_file` 都要你点一次确认，第一天就会有人把模式改成 auto，闸门等于白设。

![图 4 一次工具调用要过的三道闸：代码校验、人工批准、模型审核，成本从低到高](/img/032-building-a-harness/fig-04.svg)

上下文削减用两条便宜策略：单块封顶 4000 字，`compact` 只压最近六条之外的工具结果。取舍依据是时间相关性：十步前读过的文件大概率已经用完，留摘要就够；最近一步的报错必须原样保留，那正是下一步要处理的东西。不做摘要式压缩是有意的范围决策，规则式裁剪的好处是行为可预测、可测试。

记忆这块我第一次就做错了，值得写进文章。结构（task/files/notes 三个桶）和落盘都做了，但「跑完一个工具记一笔」这个动作没接进循环，第一次真实运行完发现记忆是空的。修复之后才算明白：记忆的难点在每一轮都要真的记账，光把结构定义出来不算。这也解释了为什么验收标准必须写成可断言的测试，而不是「支持工作记忆」这种形容词。

有界委派的绳子拴三处：子 agent 拿只读工具箱、步数默认 3、深度到顶就不再注册 delegate。最后一条是结构性防御，不靠提示词自律。提示词可以被模型忽略，结构不能。

## 六、验证：测试与真实运行

验证分两层。先离线：103 个用例，全部用临时目录和假模型客户端，不联网，跑完不到一秒。数量本身不重要，重要的是它们全部兑现了第四章 4.2 那一刀：`ModelClient` 是协议，假客户端按脚本回放，循环的四种分支（正常结束、审核拒绝、批准拒绝、步数上限）全部离线覆盖。然后在线：真模型、真仓库、真改动。离线测试保证「代码没写错」，在线这一轮回答「这套设计真的能干活吗」。

### 6.1 实验设置

对象还是第二节那个 `demo-repo`：两个文件，`calc.py` 里 `add` 用了减法、`mean` 多减了 1，`python -m unittest` 两个用例全红。运行环境是 Windows，模型走 OpenAI 兼容接口调 `deepseek-v4.1-flash`，批准模式设为 `auto`（这一轮要看的是流程能不能跑通，人工闸的 y/N 交互留给读者自己试）。入口命令就一行：

```bash
python cli.py --cwd demo-repo --approval auto --max-iterations 8 "跑一下 python -m unittest，把失败的测试修好。只改 calc.py。"
```

观察四个指标：模型调用了几次、工具执行了什么、文件最终改了哪里、墙钟多少秒。

### 6.2 运行过程

18 秒跑完。整个过程 5 次决策调用加 7 次审核调用，一共 12 次模型请求，时间线如下。

![图 5 一次真实运行的时间线：输入一句话，输出两行 diff，中间每一步都过三道闸](/img/032-building-a-harness/fig-05.svg)

值得逐段解释模型为什么这么做。第一次决策它没有急着改，先 `list_files` 看仓库结构：任务说「只改 calc.py」，它得先确认这个文件存在、周围还有什么。第二步同时读源码和测试，并跑了一遍测试拿到 `FF`：先弄清「错在哪」，再动手。第三步的诊断文字说明它定位到了两处错误，分两次 `patch_file` 各改一处。第四步重跑测试，`..` 表示两个用例都过了。第五次决策不再调工具，回纯文本收尾。

这个顺序没有写死在任何提示词里。系统提示的 RULES 只约束「改之前先读」「完成后用纯文本总结」这类粗线条行为，具体路径是模型看着现场自己选的。这正是 harness 的价值：把环境组织好，模型的行为自然像样。

每个工具调用之前都有一道审核，7 次全部 approved，理由各不相同但都指向「服务于当前任务」：读文件被批准因为「直接服务于修复」，跑命令被批准因为「验证修复的必要步骤」。第三道闸没有白花，它在每个动作上多花一次便宜调用，换来的是危险动作有人过目。

### 6.3 结果

改动只落在 `calc.py` 的两行上，独立验证通过：

```diff
 def add(a, b):
-    return a - b
+    return a + b

 def mean(values):
-    return sum(values) / len(values) - 1
+    return sum(values) / len(values)
```

改动之后在仓库外单独跑 `python -m unittest`，输出 `Ran 2 tests ... OK`。任务约束「只改 calc.py」满足，`test_calc.py` 一个字节没动。

会话文件里还留着这一轮的工作记忆：`files` 记着 `calc.py` 和 `test_calc.py`，`notes` 有五条工具摘要。也就是说，这轮之后继续追问「刚才改了什么」，模型不用重读文件就能答上来。这正是第五节补上记账之后才有的能力。

### 6.4 成本

12 次模型调用（5 次决策 + 7 次审核），墙钟 18 秒，工具全部本地执行不花钱。审核占了 7 次，超过一半，这是三道闸的价格标签。如果你只跑小任务，可以把审核角色换成更便宜的模型（`reviewer_setting` 支持单独配置），或者不装这道闸。可选，正是它作为组件的意义。

## 七、复盘：四处裂缝与后续

设计和实现都能讲清楚，但真跑起来的坑不在设计图里。四个都是实测才暴露的，它们有一个共同点：都出在「假设」上。

第一个坑假设了审核模型会按角色行事。最初把整段对话历史丢给它，让它判断这次调用该不该执行。它不回判断，而是顺着历史继续调工具，`finish_reason` 是 `tool_calls`。历史里全是助手在调工具的记录，它自然认为自己也该调。改成只给三样：当前任务、最近几条工具结果、待审的那次调用。这条经验没法从接口设计推出来，它关于模型的行为，只能靠跑。

第二个坑假设了消息序列天然合法。审核发生在工具执行之前，此时 session 末尾是一条带 `tool_calls`、却还没有对应 `tool` 结果的助手消息。这种「悬空」序列发给模型，网关直接返回空内容。审核前先摘掉这条消息。讽刺的是，这个坑恰恰是加第三道闸引出来的，多一道安全机制，多一类序列问题。

第三个坑假设了运行环境。Windows 默认 GBK，控制台打印中文、子进程抓输出、`git status` 遇到中文文件名，三处都抛异常，都要显式指定 UTF-8。不影响架构，但会把「明明代码没错」的排查拖一晚上。

第四个坑假设了协作边界。写的时候开了两个子 agent 并行，一个写工具闸门，一个写上下文和存储。任务描述里写了各自只碰哪两个文件，但漏了 `roles.py` 的归属，两边都以为自己可以动它，于是一边重写、另一边正在跑测试，短暂出现 `NameError: ToolResult 未定义`。文件归属比接口归属更容易被忽略：接口是显式的，import 错了编译期就报；文件是隐式的，跑到一半才炸。

已知不足照旧列在这：并行工具调用、摘要式压缩、多层委派、多模态都没做。下一步最想补摘要式压缩，因为现在规则式裁剪把老结果压掉之后，细节再也回不来了，而真实任务里经常出现「十步前读过的那个文件又要用了」。

代码在 [Potterluo/mini-agent-harness](https://github.com/Potterluo/mini-agent-harness)，README 按同样的脉络组织，clone 下来配上自己的 key 就能跑。
