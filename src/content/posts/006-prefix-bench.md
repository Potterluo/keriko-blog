一个 64K 的前缀被 5 个请求复用，理论收益很容易算：不走缓存的 prefill 计算量是 5n，走缓存是 n 加 5，省掉八成。搬到真机上，测出来的可能是六成，也可能是负数。

差异来自三处：命中率、淘汰策略、前缀匹配的粒度。大多数 benchmark 只在单次请求上量延迟，这三样都测不出来。PrefixBench 想补的就是这一块。

## 前缀复用在引擎内部发生在哪

推理引擎做前缀复用，粒度是 block。vLLM 的自动前缀缓存按 block 内的 token 算哈希，存下哈希链，新请求带着同样的前缀进来时逐块比对，命中哪几块就跳过哪几块的 prefill。

命中判定有三个前提：block 边界对齐、前缀逐 token 一致、缓存还没被淘汰。第一条最容易被忽略。前缀差一个 token，从差异处开始的所有块全部失效，命中率直接掉到零。

这也解释了为什么「共享前缀 + 不同问题」值得单独测。它同时考验匹配精度和缓存容量，而单请求测试只考验前者。

## 样本怎么组织

每条样本是一组，不是一个请求：一份共享前缀，加 2 到 5 个变体问题。这样一次运行的语义就是「同一个前缀被复用了 m 次」，m 由样本自己决定，不靠压测工具去猜。

长度分五档，8K 到 128K：

| 档位 | 样本数 | 平均 token |
| ---- | ------ | ---------- |
| 8K   | 4,419  | 6,246      |
| 16K  | 5,005  | 12,367     |
| 32K  | 5,841  | 24,174     |
| 64K  | 7,277  | 45,856     |
| 128K | 8,713  | 96,000     |

档内长度服从正态分布，不取固定值。原因很实际：固定长度永远不会落在淘汰阈值附近，而系统最脆的地方就是那里。真实请求的长度也不会恰好等于 8K，它在均值附近波动，偶尔给出一个边界值。

场景分四类：文档理解、代码生成、对话交互、推理问答，中英文都覆盖。全部样本 31,255 条，10 个文件，按档位和场景切分，平均每个前缀挂 3.2 个变体问题。64K 和 128K 两档合计占了一半以上，因为前缀复用的收益在这两档才明显。

## 该量的四个指标

跑完一轮，值得看的是下面四个，平均延迟降了多少反而不说明问题。

命中率。vLLM 的 metrics 里有 `gpu_prefix_cache_hit_rate`，直接取。命中率低先查 block 对齐和前缀长度，别先怀疑缓存容量。

首 token 延迟。这是复用收益最直接的体现，因为 prefill 被省掉了。要跟同一模型未命中时的数据比，不要跟另一个模型比。

KV 占用峰值。缓存占的显存和「跳过计算」省下的显存在同一块 GPU 上，容易一边降延迟一边把并发压下去。

未命中时的额外开销。哈希计算和块比对不是免费的，前缀很短时这笔开销可能超过收益，所以数据集里留了 8K 这一档。

## 那张收益表怎么读

之前的版本在这里放过一张表，列了 12.3 秒降到 2.1 秒这样的数。那张表是按公式推的量级，不是任何一台机器上的实测，很容易被当成实测引用，这次删掉了。

想要本机的数只有一条路：自己跑。同一份前缀先跑 1 个请求拿基线，再跑 5 个请求，看首 token 延迟和命中率怎么变。同时记录未命中时的数据，否则提升幅度没有分母。

有一点能在纸面上定下来：收益的上界由复用次数和前缀长度决定，跟模型大小无关。m 个请求共享一个长度 n 的前缀，prefill 的计算量从前者的乘积降到后者之和，省掉的比例只跟 m 和 n 有关。实际能拿到多少，取决于命中率，那是工程问题。

## 怎么用

数据集在 ModelScope：https://modelscope.cn/datasets/keriko/PrefixBench

10 个文件按长度档和场景切分，每条记录包含共享前缀、变体问题列表、以及期望的复用次数。接评估工具时把「组」展开成连续请求即可，前缀相同的请求必须排在一起，打散了测的是随机命中。

vLLM 侧打开自动前缀缓存：

```bash
vllm serve <model> --enable-prefix-caching
```

这个开关在 vLLM V1 里默认就开着，显式写上只是让配置可见。测量时把并发固定住，先预热一轮，再采数。

## 它测不出的东西

多实例共享缓存测不了。像 UCM、LMCache 这种把 KV 落到主机内存或远端存储的方案，复用发生在进程之间，不在单进程的 block 表里。

真实的对话前缀也不规则。多轮对话里，前缀是一步步长出来的，中间夹着工具调用的输出，形状和「一次给一份长文档」完全不同。这一块目前没有好的公开数据集，只能自己录。

淘汰压力同样测不出来。样本里的复用发生在很短的时间窗内，压不出「缓存被别的请求挤掉」这种情况。要测这个，得把缓存容量调小，或者把不同前缀的请求混着发。
