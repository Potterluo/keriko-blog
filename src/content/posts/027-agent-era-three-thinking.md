上一篇讲 Agent 时代的课程，讲的是「学什么」；这篇接着讲「怎么把东西做对」。起点是我和一个朋友的三句话：三种思维是三个观察维度；优秀的工程师不该只会解决问题，还要知道什么问题值得解决；以及——真正让我改变说法的第三句——**用户的思维是用户的心理模型，产品的思维是假设的用户模型，工程思维是真实的实现模型**（这句出自 2017 年的一篇[旧文](https://www.woshipm.com/pmd/568076.html)）。

这句话比「需求—设计—实现」高一个层次。它说的不是三个阶段，是三个世界。

文章中间有一处我讲错了，被人当场反驳：「对工程师来说，交付的永远是一个高可用的确定性工具，而不全是为 Agent 而生。」我认为这个反驳是对的，所以把修正过程原样留在了第六节——删掉它，这篇就变成一篇正确的废话。

## 0. 先说结论

1. **三种思维不是三种能力，是三个模型。** 用户模型是期望世界，产品模型是设计世界，工程模型是现实世界。三者之间的信息差是结构性的，不是沟通态度问题。
2. **Agent 时代最大的位移不在「谁来做」，而在「模型之间怎么对上」。** 用户从「操作功能」走向「委托目标」，产品从「功能集合」走向「能力集合 + 责任边界」，工程则基本没变。
3. **工程思维不该被 Agent 化绑架。** 交付物始终是可用的确定性系统；Agent 只是这套系统新增的一类使用者，不是它的目的。
4. **闭环的终点不是「执行完成」，是「价值确认」。** 这三个「完成」必须分开算，混在一个词里，是 Agent 时代最容易发生的自欺。

## 1. 一个场景：大模型推理性能测试平台

选这个场景，是因为它同时有传统软件的形态、复杂的工程约束，也很容易引入 Agent——三件事都齐了。

平台面向模型开发者、推理框架工程师和 AI Infra 团队，提供性能测试、数据采集、指标分析和报告生成。传统用法是七步：选模型和框架 → 配硬件与推理参数 → 选数据集 → 设并发和输入输出长度 → 启动任务 → 看 TTFT / TPOT / 吞吐 → 对比不同配置。

Agent 进来之后，用户可能只说一句：

> 帮我比较 Qwen3-32B 在 vLLM 和 SGLang 下的推理性能，并发测 1、8、16、32，用相同的权重、数据和硬件，最后分析差异并出报告。

表面上看，这只是多了一个对话入口。但如果认真拆，三个模型都动了——而且动的方式完全不同。

## 2. 三个模型：期望世界、设计世界、现实世界

![图 1 三个模型与它们之间的转译：用户模型是期望世界（用户认为事情应该是什么样），产品模型是设计世界（我们假设用户需要什么、怎么组织），工程模型是现实世界（系统实际如何运行）；相邻两层之间必须做一次转译，每一次转译都可能损耗，产品设计的工作就是让三者可以互相指认](/img/agent-era-course-thinking/fig-01.svg)

同一个「KVCache 能不能持久化」，三个模型问出来的问题完全不是一个东西：

- **用户模型问结果**：重启了为什么缓存就没了？能不能像数据库那样存着，下次直接读？
- **产品模型问定义**：哪些缓存该持久化？怎么判断可复用？生命周期怎么管？怎么兼容不同引擎？
- **工程模型问代价**：Block 怎么序列化？GPU/CPU/SSD 之间怎么传？并发读写怎么保证一致？索引和失效怎么管？

三者描述的是同一个问题，只是抽象层次不同。这也是为什么「把需求讲清楚」这个动作经常失败——你以为自己在补充信息，其实你在跨世界翻译，而每个世界都有一套自己的词汇表。

## 3. 用户思维：从操作功能到表达目标

传统软件的用户模型，研究的是人怎么操作软件：谁是用户、有什么需求、如何理解界面、通过什么路径完成任务、怎样降低学习成本。产品经理据此设计配置页、任务列表、曲线图、报告页。

Agent 进来之后，用户不一定亲自操作任何一个功能。他更关心五件事：我要完成什么任务、期望得到什么结果、有哪些约束、哪些可以交给 Agent 自主完成、哪些必须我拍板。

于是同一个诉求，说话方式变了：

- 传统用户：「我需要一个性能对比功能。」
- Agent 时代的用户：「帮我找出这两个框架在高并发下的差异。」

前者描述**想用的功能**，后者描述**想解决的问题**。这不是措辞的变化，是委托关系的变化。

| 维度     | 传统         | Agent 时代                             |
| :------- | :----------- | :------------------------------------- |
| 用户位置 | 直接操作者   | 委托人（Agent 是代理操作者）           |
| 表达内容 | 功能需求     | 目标、意图、约束、授权范围             |
| 成功判定 | 功能可用     | 结果满足预期                           |
| 主体数量 | 单一人类用户 | 人类用户 + 用户侧 Agent + 服务侧 Agent |

多主体这一条值得单独强调。系统可能同时面对三种主体：人类用户（要目标、体验、信任、控制权）、用户侧 Agent（要任务完成、工具可用性、执行效率）、服务侧 Agent（要协议、权限、可发现的能力）。于是出现了新问题：**产品该优先服务人，还是优先服务人的 Agent？**

一个对人类阅读很漂亮的站点，对 Agent 可能结构混乱、信息取不出来；一个对 Agent 友好的 API，人类又觉得难用。未来很可能要同时提供两套体验：面向人的 Human Experience，和面向 Agent 的 Agent Experience。这不是「加个 API」那么简单，是使用者本身变了。

但有一条底线不能松：**Agent 是代理人，不是委托人。** 代理人的理解永远可能偏离委托人的真实意图，所以「意图确认」这个环节不能因为 Agent 看起来懂了就省掉。

## 4. 产品思维：从功能集合到能力与责任边界

传统产品的核心是把需求抽象成功能，再用交互把功能串起来。Agent 时代，这个对象变了——产品不再是「一堆功能 + 一条预设路径」，而是「一组可组合的能力 + 一套行为规则」。

![图 2 一个平台、两类使用者、一层确定性内核：人类用户走 Web UI 和 CLI，Agent 走 MCP、Tool 和 API；两者进入同一套能力层（校验配置、创建任务、查询状态、取原始数据、生成报告），最终落到同一层确定性工程内核。交互可以多套，执行逻辑不该复制](/img/agent-era-course-thinking/fig-02.svg)

具体有四层变化：

1. **从功能设计到能力设计。** 过去关注「提供什么功能」，现在还要关注「系统能提供哪些可组合的能力」，以及每个能力的输入输出契约。但传统 UI 不会消失——复杂配置、实时监控、专业分析，人还是要有好界面。
2. **从固定流程到动态编排。** 路径不再完全由设计师预先定义，Agent 按目标和执行状态选路。于是产品设计多了一份工作：定义任务拆解规则、失败恢复策略、人工介入条件。
3. **从功能边界到责任边界。** 这是我认为最容易被忽略的一条。「Agent 能做什么」和「Agent 应该做什么」是两件事：

   | 动作           | 是否可交给 Agent           |
   | :------------- | :------------------------- |
   | 查询性能数据   | 可自主完成                 |
   | 创建测试任务   | 按授权自主完成             |
   | 占用大量 GPU   | 需要资源配额与审批         |
   | 改生产环境配置 | 需要更严格的权限与人工确认 |

4. **从功能验收到目标验收。** 传统验收看「功能是否符合需求」。Agent 参与后还要判断「整个任务是否真的完成」。比如两个框架都跑完了，但用的测试数据不一致——每个功能都正常，这次对比依然没有价值。所以产品要定义的不只是功能标准，还有结果质量与任务完成标准。

## 5. 工程思维：我一开始讲错了

这一节是我要专门留出来的部分。

我最初的说法是：Agent 时代，工程模型正在从「构建软件」变成「构建 Agent 能够可靠工作的环境」。听起来挺顺，但它把两件事混成了一件：

- **Agent Engineering**：把 Agent 本身当作交付物去构建（Coding Agent、研究 Agent 那种产品）。
- **工程思维**：保证一个系统正确、稳定、可维护、可演进。

前者的确是新增的领域，后者并没有变。我把特例当成了通则，这是我那段分析里最大的偏差。

被反驳之后我重新想了一遍，结论是：**工程师交付的东西，始终是一个高可用、确定性、可运维的系统；Agent 只是它新增的一类使用者。**

传统平台要保证的事，一条都没少：

- 测试任务按定义执行，参数合法，语义不被调用者改变；
- 数据真实、完整、可复现；
- 指标计算正确，多任务并发时资源隔离；
- 异常能恢复，失败状态准确反馈。

现在只不过多了一条：这些保证，要同时对人和 Agent 成立。于是工程量清单里加了几项新东西——API 语义清晰、工具契约明确、关键操作幂等、异步任务状态可查、权限可授权、操作可审计、错误信息足够明确让调用者知道下一步该干什么。

注意这些要求的出发点。它们不是「为了迎合 Agent 而改造系统」，而是「让系统能被更多类型的调用者可靠地使用」。同一个能力，人、Agent、Jenkins、别的系统都该走同一套实现；为了 Agent 单独复制一份测试逻辑，是最糟的做法——它会让「确定性」出现两个版本。

还有一个我认为更值得说的反转：**Agent 越强，确定性越贵。**

人有经验，能兜住一些模糊状态：接口返回一句含糊的错误、HTTP 200 但业务没真正完成、异步任务还没结束——人看着不对劲会去查。Agent 不会，它会顺着这个模糊状态继续往下执行，而且执行得很顺畅。

所以 Agent 时代的系统，反而需要更明确的状态定义、更严格的契约、更可靠的异常处理和更完整的可观测性。这不是工程思维向 Agent 思维投降，是工程系统要承担更多可靠性责任。

## 6. 分界线：概率性决策，确定性执行

![图 3 概率性与确定性的分界：左侧由 Agent 负责理解目标、制定计划、选择方案、解释结果，右侧由工程系统负责校验参数、管理资源、执行任务、采集与计算；中间是一道契约，规定能调什么、怎么失败、状态怎么查。智能放在需要判断的地方，确定性放在需要保障的地方](/img/agent-era-course-thinking/fig-03.svg)

落到架构上，我倾向于画一条很硬的线：

- **Agent 可以决定**：理解目标、制定计划、选择测试方案、分析结果、给优化建议。
- **工程系统必须负责**：校验参数、管理资源、执行测试、采集数据、计算指标、保存结果。

一句话：**Agent 可以决定跑什么，但不能决定结果对不对。**

这条线画清楚之后，很多争论就不用吵了。比如「要不要让 Agent 自己重试」——重试策略属于工程能力（幂等、退避、次数上限），Agent 只决定「是否值得重试」。把不断重试当成可靠性机制，只是让故障更持久。

## 7. 完整闭环：九个环节，三种「完成」

三个模型要真正串起来，靠的不是一个对话入口，而是一条能自我校验的任务链：

![图 4 九步任务闭环：目标提出、目标结构化、任务规划进入执行准备，执行与观测之后是结果验证，再交付、再收集用户反馈并回到下一轮。验证不通过时可以回到规划或准备阶段，反馈则开启新的任务](/img/agent-era-course-thinking/fig-04.svg)

1. **目标提出。** 用户给的是目标，不是步骤。Agent 先要问清：测什么、比什么、约束是什么、要什么交付物、哪些信息还缺。缺的信息如果影响结论正确性，必须问，不能编。
2. **目标结构化。** 把自然语言变成任务定义：对象、变量、条件、关注指标、交付物、成功标准。这一步是用户模型向产品模型的转换，也是整条链最容易偷工的地方。
3. **任务规划。** 拆成有依赖的子任务：环境检查、版本确认、配置校验、数据准备、两轮测试矩阵、数据校验、指标比较、报告生成。哪些能并行、哪些必须串行，由资源规则决定，不听 Agent 的直觉。
4. **执行准备。** 资源够不够、权重在不在、版本对不对、配置合不合法、会不会影响别人、调用者有没有权限。普通任务按预授权自动跑，高资源消耗或生产变更必须走审批。
5. **任务执行。** Agent 调能力，不重写实现。真正干活的是确定性内核：调度、隔离、执行、采集、状态维护、异常处理。
6. **过程观测。** 启动失败、OOM、进程异常退出、数据不完整、指标偏离预期——Agent 根据真实状态调整，而不是发完请求就宣布完成。
7. **结果验证。** 这是全链最值钱的一步。两个框架都跑完了，但可能：输入数据不同、环境变了、模型配置不一致、输出长度不同、某组数据缺失、样本太少波动过大。任何一条没查，报告就没有参考价值。
8. **结果交付。** 交付物不能只有一段自然语言总结，还要有任务记录、完整配置、版本信息、原始数据、指标计算、对比图表、异常说明、可追溯的执行记录。数据不足以支撑某个结论时，要明说，不能为了让报告看起来完整而编造确定性。
9. **用户反馈。** 报告交付不是终点。「为什么 SGLang 的 TPOT 更低」「能不能再测 TP8」「这个结果能不能当下一轮基线」——这些反馈会变成新任务，也会暴露产品能力的缺口。

这条链的关键，是它有三个**互不等价**的完成状态：

| 完成状态 | 含义                       | 谁说了算       |
| :------- | :------------------------- | :------------- |
| 执行完成 | 计划中的操作都做完了       | 系统           |
| 目标达成 | 结果满足预先定义的验收标准 | 产品定义的判据 |
| 价值确认 | 用户认可结果解决了实际问题 | 用户           |

Agent 能把前两个做到很好，第三个它替不了。把三者压成一个「已完成」，就是这套体系里最体面的一种自欺。

## 8. 回到三种思维

| 思维模型 | 传统时代                 | Agent 时代                                 |
| :------- | :----------------------- | :----------------------------------------- |
| 用户思维 | 理解用户如何使用软件     | 理解用户要实现什么目标、如何委托           |
| 产品思维 | 定义功能、流程与交互     | 定义能力、编排、自主权与结果标准           |
| 工程思维 | 构建可靠、确定的软件系统 | 仍然构建可靠、确定的软件系统，多一类使用者 |

我认为这三种思维的核心职责一个都没消失，只是各自的关注范围扩了：用户思维从操作习惯扩到意图与委托；产品思维从功能设计扩到能力组织与责任边界；工程思维**不该被 Agent 化绑架**，它要守住确定性，同时让系统接得住新的使用者。

所以最后落两句：

- **AI Agent 不应该成为所有软件系统的目的，但应该成为所有软件系统都要考虑的一类使用者。**
- 智能负责理解、判断、组织任务；可靠的系统负责执行、约束、保障；人负责定义什么值得做，并确认结果真的有用。

还有一句风险提示，我认为它是这套框架真正的软肋：**Agent 时代最大的风险，不是它不会做事，而是它把错误的理解、错误的产品定义、错误的工程实现，用极高的速度串成一条链。** 过去一个错误需求要走几天才变成错误代码，现在可能几分钟就交付了。

效率提升了，犯错的速度也提升了。所以三个模型之间真正要练的能力，不是怎么把信息传得更快，而是两件更难的事：**意图一致性**——做的是不是用户真正要的；**结果可验证性**——能不能证明做成了。这两条守不住，Agent 越快，偏得越远。
