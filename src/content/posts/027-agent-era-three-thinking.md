上一篇写 Agent 时代的课程，谈的是学什么。这篇谈怎么把东西做对。

起因是朋友转来的一句话：用户的思维是用户的心理模型，产品的思维是假设的用户模型，工程思维是真实的实现模型。出自 2017 年的一篇[旧文](https://www.woshipm.com/pmd/568076.html)。这句比「需求、设计、实现」那套说法准确，因为它讲的不是三个步骤，是三个世界：用户以为的、我们假设的、系统实际跑的。

写到一半我被反驳了一次。对方说，对工程师来说，交付的永远是一个高可用的确定性工具，不全是为 Agent 而生。这话我认，所以第五节写的是改口的过程。省掉这段，结论会变成一句谁都同意、谁也用不上的话。

## 1. 场景：大模型推理性能测试平台

拿推理性能测试平台做例子，因为它同时有传统软件的形态、复杂的工程约束，也容易接 Agent。

平台面向模型开发者、推理框架工程师和 AI Infra 团队，做性能测试、数据采集、指标分析和报告生成。传统用法七步：选模型和框架、配硬件与推理参数、选数据集、设并发和输入输出长度、启动任务、看 TTFT / TPOT / 吞吐、对比不同配置。

接上 Agent 之后，用户可能只说一句：

> 帮我比较 Qwen3-32B 在 vLLM 和 SGLang 下的推理性能，并发测 1、8、16、32，用相同的权重、数据和硬件，最后分析差异并出报告。

看起来只是多了一个对话入口。拆开看，三个模型都动了，动的地方还不一样。

## 2. 三个模型

![图 1 三个模型与它们之间的转译：用户模型是期望世界（用户认为事情应该是什么样），产品模型是设计世界（我们假设用户需要什么、怎么组织），工程模型是现实世界（系统实际如何运行）；相邻两层之间必须做一次转译，每一次转译都可能损耗，产品设计的工作就是让三者可以互相指认](/img/agent-era-course-thinking/fig-01.svg)

同一个「KVCache 能不能持久化」，三个模型问出来的问题不一样：

- 用户问结果：重启了为什么缓存就没了？能不能像数据库那样存着，下次直接读？
- 产品问定义：哪些缓存该持久化？怎么判断可复用？生命周期怎么管？怎么兼容不同引擎？
- 工程问代价：Block 怎么序列化？GPU/CPU/SSD 之间怎么传？并发读写怎么保证一致？索引和失效怎么管？

三个世界说的是同一件事，只是词汇表不同。「把需求讲清楚」这个动作经常失败，因为它默认存在一个中立的说法，而实际上每补一次信息都在翻译。

## 3. 用户思维：从操作功能到表达目标

传统软件的用户模型研究人怎么操作软件：谁是用户、有什么需求、如何理解界面、走什么路径完成任务、怎样降低学习成本。产品经理据此设计配置页、任务列表、曲线图、报告页。

接上 Agent 之后，用户不一定亲自操作任何一个功能。他关心的是另外五件事：要完成什么任务、期望什么结果、有哪些约束、哪些能交给 Agent 自主完成、哪些必须自己拍板。

同一个诉求，说法变了：

- 传统用户：我需要一个性能对比功能。
- Agent 时代的用户：帮我找出这两个框架在高并发下的差异。

前者说的是想用的功能，后者说的是想解决的问题。位置也从操作者变成了委托人。

| 维度     | 传统         | Agent 时代                             |
| :------- | :----------- | :------------------------------------- |
| 用户位置 | 直接操作者   | 委托人（Agent 是代理操作者）           |
| 表达内容 | 功能需求     | 目标、意图、约束、授权范围             |
| 成功判定 | 功能可用     | 结果满足预期                           |
| 主体数量 | 单一人类用户 | 人类用户 + 用户侧 Agent + 服务侧 Agent |

多主体这一条的影响比看起来大。系统可能同时面对三种主体：人类用户要目标、体验、信任和控制权；用户侧 Agent 要任务能完成、工具可用、执行效率高；服务侧 Agent 要协议、权限和可发现的能力。

于是有了一个新问题：产品该优先服务人，还是优先服务人的 Agent。一个对人类阅读很漂亮的站点，对 Agent 可能结构混乱、信息取不出来；一个对 Agent 友好的 API，人又觉得难用。以后很可能要给两套体验，一套 Human Experience，一套 Agent Experience。这不是加个 API 的事，使用者本身变了。

底线没变：Agent 始终是代理人，最终决定权在委托人手里。代理人的理解可能偏离委托人的真实意图，所以意图确认这一步不能因为 Agent 看起来懂了就省掉。

## 4. 产品思维：从功能集合到能力与责任边界

传统产品的做法是把需求抽象成功能，再用交互把功能串起来。Agent 时代，产品提供的是一组能组合的能力，外加一套约束行为的规则。

![图 2 一个平台、两类使用者、一层确定性内核：人类用户走 Web UI 和 CLI，Agent 走 MCP、Tool 和 API；两者进入同一套能力层（校验配置、创建任务、查询状态、取原始数据、生成报告），最终落到同一层确定性工程内核。交互可以多套，执行逻辑不该复制](/img/agent-era-course-thinking/fig-02.svg)

具体落在四件事上。

一是功能变成能力。过去问「提供什么功能」，现在还要问「能提供哪些可组合的能力」，每个能力的输入输出契约是什么。传统 UI 不会消失，复杂配置、实时监控、专业分析还是得有好界面。

二是路径从固定变成动态。执行顺序不再完全由设计师定，Agent 按目标和执行状态选路。产品设计因此多了一份工作：定任务拆解规则、失败恢复策略、人工介入条件。

三是边界从功能变成责任。这一条最容易被漏掉。「Agent 能做什么」和「Agent 应该做什么」是两件事：

| 动作           | 是否可交给 Agent           |
| :------------- | :------------------------- |
| 查询性能数据   | 可自主完成                 |
| 创建测试任务   | 按授权自主完成             |
| 占用大量 GPU   | 需要资源配额与审批         |
| 改生产环境配置 | 需要更严格的权限与人工确认 |

四是验收从功能变成目标。传统验收看功能符不符合需求，Agent 参与后还要判断整个任务有没有真的完成。两个框架都跑完了，但测试数据不一致，每个功能都正常，这次对比依然没有价值。所以产品要定两份标准：功能标准，和结果质量与任务完成标准。

## 5. 工程思维：我改过一次口

我最初写的是：Agent 时代，工程模型正在从「构建软件」变成「构建 Agent 能够可靠工作的环境」。

这句话把两件事混成了一件。Agent Engineering 是把 Agent 本身当交付物，Coding Agent、研究 Agent 都属于这类；工程思维是保证一个系统正确、稳定、可维护。前者确实是新领域，后者没变。我把特例当成了通则。

朋友的反驳更直接：工程师交付的永远是高可用的确定性工具。我认下来之后发现，原来的清单一条都不用改。任务按定义执行，参数合法，语义不被调用者改变；数据真实、完整、可复现；指标算得对，并发时资源隔离；异常能恢复，失败状态准确反馈。

多出来的只有一句：这些保证要同时对人和 Agent 成立。于是工程量清单里添了几项，API 语义清晰、工具契约明确、关键操作幂等、异步任务状态可查、权限可授予、操作可审计、错误信息能告诉调用者下一步干什么。

这些要求的出发点容易搞反：它们是为了让系统能被更多调用者可靠地使用，跟迎合 Agent 无关。同一份能力，人、Agent、Jenkins、别的系统都该走一套实现。为 Agent 单独复制一份测试逻辑是最坏的做法，确定性会出现两个版本。

反过来说也成立：Agent 越强，确定性越值钱。人有经验，能兜住模糊状态。接口回一句含糊的错误，HTTP 200 但业务没真正完成，异步任务还没结束，人看一眼觉得不对劲会去查。Agent 会顺着这个状态继续往下跑，而且跑得很顺。

所以这类系统反而需要更明确的状态定义、更严格的契约、更可靠的异常处理、更完整的可观测性。这笔责任是工程系统多担的，跟 Agent 会不会思考无关。

## 6. 分界线：概率性决策，确定性执行

![图 3 概率性与确定性的分界：左侧由 Agent 负责理解目标、制定计划、选择方案、解释结果，右侧由工程系统负责校验参数、管理资源、执行任务、采集与计算；中间是一道契约，规定能调什么、怎么失败、状态怎么查。智能放在需要判断的地方，确定性放在需要保障的地方](/img/agent-era-course-thinking/fig-03.svg)

落到架构上，这条线可以画得很硬。Agent 决定理解目标、制定计划、选测试方案、分析结果、给优化建议；工程系统负责校验参数、管理资源、执行测试、采集数据、算指标、存结果。

Agent 可以决定跑什么，结果对不对由系统说了算。

线画清楚了，很多争论就没有了。比如要不要让 Agent 自己重试：重试策略属于工程能力，幂等、退避、次数上限都写在系统里，Agent 只回答值不值得再试一次。把不断重试当成可靠性机制，只是让故障拖得更久。

## 7. 完整闭环：九个环节，三种「完成」

三个模型要串起来，靠的是能自我校验的任务链，不是那个对话入口。

![图 4 九步任务闭环：目标提出、目标结构化、任务规划进入执行准备，执行与观测之后是结果验证，再交付、再收集用户反馈并回到下一轮。验证不通过时可以回到规划或准备阶段，反馈则开启新的任务](/img/agent-era-course-thinking/fig-04.svg)

1. 目标提出。用户给的是目标，不是步骤。Agent 先问清：测什么、比什么、约束是什么、要什么交付物、哪些信息还缺。缺的信息如果影响结论正确性，必须问，不能编。
2. 目标结构化。把自然语言变成任务定义：对象、变量、条件、关注指标、交付物、成功标准。这一步是用户模型转成产品模型，也是整条链最容易偷工的地方。
3. 任务规划。拆成有依赖的子任务：环境检查、版本确认、配置校验、数据准备、两轮测试矩阵、数据校验、指标比较、报告生成。哪些能并行、哪些必须串行，由资源规则决定，不听 Agent 的直觉。
4. 执行准备。资源够不够、权重在不在、版本对不对、配置合不合法、会不会影响别人、调用者有没有权限。普通任务按预授权自动跑，高资源消耗或生产变更走审批。
5. 任务执行。Agent 调能力，不重写实现。干活的是确定性内核：调度、隔离、执行、采集、状态维护、异常处理。
6. 过程观测。启动失败、OOM、进程异常退出、数据不完整、指标偏离预期，都要按真实状态处理。发完请求就宣布完成，是这条链上最常见的短路。
7. 结果验证。这是最值钱的一步。两个框架都跑完了，但可能输入数据不同、环境变了、模型配置不一致、输出长度不同、某组数据缺失、样本太少波动过大。任何一条没查，报告都没有参考价值。
8. 结果交付。交付物不能只有一段总结，还要有任务记录、完整配置、版本信息、原始数据、指标计算、对比图表、异常说明、可追溯的执行记录。数据不足以支撑结论时明说，别为了让报告看起来完整而编造确定性。
9. 用户反馈。报告交付不是终点。为什么 SGLang 的 TPOT 更低、能不能再测 TP8、这个结果能不能当下一轮基线，这些反馈会变成新任务，也会暴露产品能力的缺口。

这条链上有三个完成状态，互不等价：

| 完成状态 | 含义                       | 谁说了算       |
| :------- | :------------------------- | :------------- |
| 执行完成 | 计划中的操作都做完了       | 系统           |
| 目标达成 | 结果满足预先定义的验收标准 | 产品定义的判据 |
| 价值确认 | 用户认可结果解决了实际问题 | 用户           |

前两个 Agent 能做得不错，第三个它替不了。三个词压成一个「已完成」，是这套体系里最容易发生的误会。

## 8. 回到三种思维

| 思维模型 | 传统时代                 | Agent 时代                                 |
| :------- | :----------------------- | :----------------------------------------- |
| 用户思维 | 理解用户如何使用软件     | 理解用户要实现什么目标、如何委托           |
| 产品思维 | 定义功能、流程与交互     | 定义能力、编排、自主权与结果标准           |
| 工程思维 | 构建可靠、确定的软件系统 | 仍然构建可靠、确定的软件系统，多一类使用者 |

三种思维的核心职责一个都没消失，扩的是范围。用户思维从操作习惯扩到意图与委托，产品思维从功能设计扩到能力组织与责任边界，工程思维守住确定性，同时接住新的使用者。

两条落点：AI Agent 不该成为所有软件系统的目的，但该成为所有软件系统都要考虑的一类使用者；智能负责理解、判断、组织任务，可靠的系统负责执行、约束、保障，人负责定义什么值得做，并确认结果真的有用。

风险在另一头。Agent 能把错误的理解、错误的产品定义、错误的工程实现，用几分钟串成一条链。过去一个错误需求要走几天才变成错误代码，现在交付得比想清楚还快。所以三个模型之间要练的是两件事：做的是不是用户要的，能不能证明做成了。
